## Executive Summary

This document presents the **final design** for process map observability in ClaudeVN, incorporating feedback and design decisions:

✅ **Event-Driven Architecture** - Compute pushes updates to Serving (NO polling)  
✅ **Near Real-Time** - < 1 second latency via WebSocket streaming  
✅ **Dynamic Activity Grouping** - Semantic grouping as process evolves  
✅ **Dual Visualization** - Both workflow graph AND timeline views  
✅ **Progressive Disclosure** - Collapsible groups manage complexity

## Core Design Decisions

### 1. Event-Driven, Not Polling ✅

**Requirement**: "I don't want polling! Compute modules can push updates."

**Design**:
- Compute emits events on activity state changes (start, complete, blocked)
- HTTP POST to Serving `/api/v1/observability/events`
- Serving Event Bus persists events and broadcasts via WebSocket
- Frontend receives updates in near real-time (< 1 second)

**Benefits**:
- **Low Latency**: < 1 second vs. 3-5 seconds with polling
- **Scalable**: Event-driven scales better than constant polling
- **Efficient**: Backend only processes on actual changes

**Implementation**: See [OBSERVABILITY_EVENT_DRIVEN.md](OBSERVABILITY_EVENT_DRIVEN.md)

---

### 2. Dynamic Activity Grouping ✅

**Requirement**: "We will need to name and group activities as we go... For instance, the first activities are decomposition and process map build. Once complete, that can be combined into 1 group (card) on the screen."

**Design**:
- Process Mapper creates semantic groups as the process evolves
- Groups like "Data Collection", "Segment Analysis", "Strategy Development"
- Completed groups collapse automatically to reduce visual clutter
- Groups can be hierarchical (nested) for complex processes
- Group names generated by Process Mapper using LLM

**Example**:
```
▶ Data Collection & Access (4 activities - 100% complete) 🟢
▼ Segment-Based Analysis (3 activities - 67% in progress) 🔵
  Activity 2a: High-Value Analysis 🔵 Active
  Activity 2b: SMB Analysis 🔴 Blocked
  Activity 2b-1: Get Pricing Data 🔵 Active
▶ Strategy Development (6 activities - 0% not started) 🟡
```

**Benefits**:
- Reduces 100 activities to 5-10 groups
- Provides semantic context ("what phase are we in?")
- Progressive disclosure (collapse completed work)

**Implementation**: See [OBSERVABILITY_ACTIVITY_GROUPING.md](OBSERVABILITY_ACTIVITY_GROUPING.md)

---

### 3. Near Real-Time (1-3 Second Latency) ✅

**Requirement**: "When I say real-time, I mean near real-time. It can be a couple seconds delayed if needed (though I don't see why the compute modules can't kick off an api call to the serving component on agent shift)."

**Design**:
```
Activity completes → Compute emits event (< 100ms)
                  → HTTP POST to Serving (< 50ms)
                  → Event Bus processes (< 50ms)
                  → WebSocket broadcast (< 100ms)
                  → Frontend UI updates (< 100ms)

Total latency: ~300ms (well under 1 second!)
```

**Implementation**:
- Compute: `ObservabilityEventClient` sends HTTP POST on activity transitions
- Serving: `ObservabilityEventBus` receives, persists, and broadcasts
- Frontend: `ObservabilityWebSocket` receives and updates UI

---

### 4. Both Workflow Graph AND Timeline ✅

**Requirement**: "I definitely want both visualizations. We can keep it simple at first, but let's make sure we provide both workflow graph and timeline list."

**Design**:

**Workflow Graph View** - Shows structure and dependencies:
```
┌──────────────────────────────────────────────────┐
│ Workflow Tab                                     │
├──────────────────────────────────────────────────┤
│                                                  │
│  ▶ Group: Data Collection (Collapsed)           │
│                                                  │
│              ↓                                   │
│                                                  │
│  ▼ Group: Segment Analysis (Expanded)           │
│     Activity 2a ──→ Activity 3a                  │
│     Activity 2b ──→ Activity 3b                  │
│                                                  │
│              ↓                                   │
│                                                  │
│  Activity 4: Synthesize                          │
│                                                  │
└──────────────────────────────────────────────────┘
```

**Timeline View** - Shows chronological sequence:
```
┌──────────────────────────────────────────────────┐
│ Timeline Tab                                     │
├──────────────────────────────────────────────────┤
│                                                  │
│ 2:00 PM │ 📋 Session Created                    │
│ 2:02 PM │ 🗺️ Process Map v1 Created            │
│ 2:03 PM │ 🎯 Activity 0: Started                │
│ 2:15 PM │ ✅ Activity 0: Completed              │
│ 2:15 PM │ 🎯 Activity 1: Started                │
│ 2:30 PM │ 🔄 Process Map v2 (Reevaluation)     │
│ 2:38 PM │ ✅ Activity 1: Completed              │
│ 3:05 PM │ ⚠️ Blocker Identified                 │
│ 3:07 PM │ 🔄 Process Map v3 (Reevaluation)     │
│         │ └─ Now ────────────────────           │
│                                                  │
└──────────────────────────────────────────────────┘
```

**Implementation**:
- Tabs in Session Detail View: `[Overview] [Workflow] [Timeline] [Resources]`
- Both views update in real-time via WebSocket
- Start simple: Basic graph layout and chronological list
- Phase 2+: Enhanced graph algorithms, time compression, zoom/pan

## Key Features

### Feature 1: Multi-Session Dashboard

**Purpose**: See all active sessions at a glance

**Shows**:
- Session ID and business goal
- Progress (X% complete, Y/Z activities)
- Active agents and compute resources
- Blockers and status
- Quick actions (View Details, Timeline, Resources)

**Real-Time Updates**: WebSocket streams session state changes

---

### Feature 2: Session Detail View

**Tabs**:
1. **Overview** - Summary stats, active agents, compute resources, blockers
2. **Workflow** - Graph visualization with collapsible groups
3. **Timeline** - Chronological event stream
4. **Resources** - Compute utilization and agent tracking

**Real-Time Updates**: Subscribe to session-specific events via WebSocket

---

### Feature 3: Activity Detail Modal

**Shows**:
- Activity goal and status
- Participants (agents and compute instances)
- Dependencies and blockers
- **Conversation Timeline** - Full exchange history with intent badges
- Outputs and key findings (Phase 6+)

**Opens on**: Click activity card in workflow or timeline

---

### Feature 4: Dynamic Activity Groups

**Created by**: Process Mapper (automatically)

**Types**:
- **Temporal**: Activities completed around same time
- **Dependency-Based**: Activities sharing same parent
- **Semantic**: Activities accomplishing same sub-goal (LLM-determined)
- **Blocker Resolution**: Activities spawned from same blocker

**UI Behavior**:
- Completed groups: Collapsed by default
- Active groups: Expanded by default
- Click to toggle expand/collapse

## Data Flow Diagrams

### Activity Start Flow

```
1. Activity Facilitator begins facilitation on Compute
         ↓
2. Compute emits ActivityStateChangeEvent
         ↓ (HTTP POST)
3. Serving /api/v1/observability/events receives event
         ↓
4. Event Bus persists to event log
         ↓
5. Event Bus updates Process Map storage
         ↓
6. Event Bus broadcasts via WebSocket
         ↓
7. Frontend receives event and updates UI
         ↓
8. User sees activity status change (< 1 second)
```

### Activity Grouping Flow

```
1. Process Mapper detects group opportunity
   (e.g., 3 activities completed, share goal)
         ↓
2. Process Mapper generates group name (LLM)
         ↓
3. Process Mapper creates ActivityGroup
         ↓
4. Compute emits ActivityGroupingEvent
         ↓ (HTTP POST)
5. Serving receives and persists group
         ↓
6. Event Bus broadcasts to subscribers
         ↓
7. Frontend receives group and re-renders workflow
         ↓
8. User sees new group card (collapsed if complete)
```

## Event Types

### 1. ActivityStateChangeEvent
Emitted when: Activity status changes (proposed → in_progress → goal_met/blocked)

### 2. ExchangeEvent (Throttled)
Emitted when: Exchange completes (every 5th exchange or important intents)

### 3. ProcessMapReevaluationEvent
Emitted when: Process map restructures (add/remove/modify activities)

### 4. BlockerEvent
Emitted when: Blocker identified during facilitation

### 5. ActivityGroupingEvent
Emitted when: Process Mapper creates activity group

## WebSocket Protocol

### Frontend → Serving

```javascript
// Subscribe to sessions
ws.send(JSON.stringify({
  action: 'subscribe',
  session_ids: ['session-abc', 'session-xyz']
}));

// Unsubscribe
ws.send(JSON.stringify({
  action: 'unsubscribe',
  session_ids: ['session-abc']
}));

// Heartbeat
ws.send(JSON.stringify({
  action: 'pong',
  timestamp: Date.now()
}));
```

### Serving → Frontend

```javascript
// Activity state change
{
  type: 'activity_state_change',
  event: { /* ActivityStateChangeEvent */ }
}

// Activity grouping
{
  type: 'activity_grouping',
  event: { /* ActivityGroupingEvent */ }
}

// Blocker identified
{
  type: 'blocker_identified',
  event: { /* BlockerEvent */ }
}

// Heartbeat
{
  type: 'ping',
  timestamp: '2025-11-25T15:30:45Z'
}
```

## Risks & Mitigations

### Risk 1: WebSocket Connection Management

**Risk**: WebSocket disconnections could miss events

**Mitigation**:
- Automatic reconnection with exponential backoff
- On reconnect, re-fetch current process map state
- Event log provides durability (can replay if needed)

### Risk 2: Event Emission Failures

**Risk**: Compute can't reach Serving to emit event

**Mitigation**:
- Fire-and-forget (Compute doesn't block on failures)
- Process Map storage is source of truth
- Frontend can re-fetch on reconnect

### Risk 3: UI Performance with Large Graphs

**Risk**: Workflow graph with 100 activities is slow to render

**Mitigation**:
- Hierarchical grouping reduces visible nodes
- Lazy rendering (only visible viewport)
- Alternative: Switch to Timeline view for very large maps
