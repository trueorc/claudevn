# ClaudeVN v2.0 Architecture: Intelligence Layer for Project-Scale AI Development

**Status:** Proposal
**Date:** 2026-03-29
**Authors:** Matt Lyons, with research synthesis by Claude

---

## 1. Executive Summary

ClaudeVN v2.0 represents a fundamental architectural shift from a multi-agent orchestration platform to an **intelligence layer that makes Claude Code work at project scale**. This redesign is motivated by both empirical research findings and practical experience with v1.0's coordination and quality issues.

Claude Code solves tasks. ClaudeVN solves **projects** — it decomposes them into the right tasks, prepares each task for efficient execution, and verifies that the results integrate correctly. It doesn't replace Claude Code or wrap it. It does the work that sits above and below what Claude Code is good at.

The core value proposition: **decomposition intelligence, context preparation, and integration verification** — the three capabilities that individual Claude Code instances fundamentally cannot provide because they lack the global project view.

## 2. Research Foundation

This architecture is grounded in findings from recent academic research on multi-agent AI systems. The key papers and their implications are summarized below. Full analysis is available in the referenced materials.

### 2.1 Multi-Agent Coordination Often Hurts Performance

**"Towards a Science of Scaling Agent Systems"** — Kim et al., Dec 2025 (UW, MIT, Microsoft, Google)
*arXiv: 2512.08296 — 14,742 runs across 180 configurations*

- Mean multi-agent improvement across all benchmarks: **-3.5%** (multi-agent systems on average hurt performance)
- Hybrid architectures (orchestrator + peer communication — closest to ClaudeVN v1.0) showed **515% overhead** and **5x worse token efficiency** than single-agent
- **Capability saturation threshold at ~45%**: once a single agent exceeds ~45% accuracy on a task, adding more agents provides diminishing or negative returns
- Error amplification: independent agents amplify errors **17.2x**, centralized architectures contain to 4.4x
- After 10 rounds of inter-agent interaction, agents share only **34% of their world state** — progressive divergence is inherent to decomposing reasoning across separate contexts
- **Key finding**: only tasks that are naturally parallelizable with no shared state during execution benefit from multi-agent approaches (Finance-Agent: +81%). Sequential, state-dependent tasks universally degrade (-39% to -70%)

**Implication for ClaudeVN**: The v1.0 hybrid orchestration model (serving hub coordinating compute instances via MCP) falls squarely in the worst-performing architecture class. The coordination machinery is a net negative for most software engineering tasks.

### 2.2 Multi-Agent Failure Modes Are Structural, Not Incidental

**"Why Do Multi-Agent LLM Systems Fail?"** — Cemri et al., ICLR 2025 / NeurIPS 2025 (UC Berkeley)
*arXiv: 2503.13657 — 1,642 annotated failure traces across 7 MAS frameworks*

14 failure modes in three categories:

| Category | % of Failures | Key Modes |
|---|---|---|
| **System Design** | 44.2% | Step repetition (15.7%), termination confusion (12.4%), task spec drift (11.8%) |
| **Inter-Agent Misalignment** | 32.3% | Reasoning-action mismatch (13.2%), task derailment (7.4%), failure to clarify (6.8%) |
| **Task Verification** | 23.5% | Incorrect verification (9.1%), incomplete verification (8.2%), premature termination (6.2%) |

- The top 4 failure modes (52.6% of all failures) are **coordination problems that don't exist in single-agent systems**
- The paper explicitly states: "improvements in the base model capabilities will be insufficient to address the full MAST" — these are structural failures, not model limitations
- Interventions (better prompts, topology changes) improved ChatDev from 25% to 40.6% — still a 59.4% failure rate
- Gains were inconsistent across models — what worked for GPT-4o didn't work for GPT-4

**Implication for ClaudeVN**: Nearly half of all multi-agent failures come from the system design itself. Better orchestration cannot fix a paradigm that inherently generates these failure modes. The architecture must minimize the surface area for these failures by minimizing inter-agent coordination.

### 2.3 Simple Pipelines Beat Complex Agent Architectures

**"Agentless: Demystifying LLM-based Software Engineering Agents"** — Xia et al., Jul 2024 (UIUC)
*arXiv: 2407.01489*

- A fixed three-phase pipeline (localize, repair, validate) with **zero autonomous agent decision-making** achieved 32% on SWE-bench Lite at $0.70/issue
- SWE-agent (a proper autonomous agent): 18.3% at $2.53/issue with 498K tokens
- The pipeline approach used **6-7x fewer tokens** and solved **75% more problems**
- Critical insight: when issue descriptions lack location clues, agent-based approaches outperform — exploration is valuable for ambiguous problems but wasteful for well-specified ones
- Adopted by OpenAI as their default approach for showcasing model performance on SWE-bench

**Implication for ClaudeVN**: The value of agent-based execution is in handling ambiguity. If ClaudeVN's decomposition layer can reduce ambiguity (producing well-specified work units with clear file targets and verification criteria), each Claude Code instance needs fewer exploration turns and produces higher quality output. The decomposition quality directly determines execution efficiency.

### 2.4 Anthropomorphic Design Constrains AI Systems

**"Thinking Beyond the Anthropomorphic Paradigm Benefits LLM Research"** — Ibrahim & Cheng, Feb 2025
*arXiv: 2502.09192*

- Empirical analysis of hundreds of thousands of papers showing growing anthropomorphic terminology in LLM research
- Identifies five constraining assumptions, including that LLMs must reason through natural language and should be evaluated on human benchmarks
- Argues "methods operating beyond linguistic constraints may drive greater advancements in LLM capabilities"

**"Large Language Models Miss the Multi-Agent Mark"** — La Malfa et al., NeurIPS 2025 (Oxford)
*arXiv: 2505.21298*

- Contemporary MAS-LLM literature appropriates multi-agent terminology without engaging with foundational MAS principles
- Most systems "lack multi-agent characteristics such as autonomy, social interaction, and structured environments"

**Implication for ClaudeVN**: v1.0's architecture — role assignment, natural language coordination, iterative exploration, market-style skill matching — models how a human development team works, not how AI systems work most efficiently. v2.0 should lean into AI-native patterns: structured state over conversation, single-pass execution over iterative loops, computational verification over AI-as-reviewer.

### 2.5 AI Coding Tools Introduce Quality Debt

**"Speed at the Cost of Quality"** — He et al., MSR 2026 (Carnegie Mellon)
*arXiv: 2511.04427*

- Large-scale study of 807 repos adopting AI coding tools
- 3-5x initial productivity surge, **but gains dissipate after two months**
- Static analysis warnings increase by **30%**, code complexity increases by **41%**
- Self-reinforcing cycle: speed creates maintenance burden

**Implication for ClaudeVN**: Quality verification is not optional — it's the critical differentiator. Without it, AI-generated code creates compounding technical debt. ClaudeVN's Layer 3 (integration verification) directly addresses the gap this paper identifies.

## 3. Critique of v1.0 Architecture

### 3.1 Coordination Surface Area

Analysis of the v1.0 execution path for a single work item reveals:

| Metric | Count |
|---|---|
| Inter-service calls per work item | ~25-30 |
| Shared state object families (Redis) | 11 |
| Synchronization mechanisms | 10 |
| Services in the critical path | 18 |
| Background monitoring loops | 3 |

### 3.2 Service Classification

**Design-time (Layer 1) — valuable, retain and strengthen:**
- GoalDecomposerService
- DecompositionValidationService
- WorkPlannerService
- CharacterizationService
- SkillSelectionService

**Execution-time (Layer 2) — currently over-engineered:**
- WorkOrchestrator (75KB)
- WorkDispatcher
- AssignmentService (37KB)
- WorkMapService (59KB)
- WorkContextEnrichmentService
- ClaudeCodeSpawner (84KB)

**Verification (Layer 3) — valuable, retain and strengthen:**
- QualityGateService
- LeadComputeService
- SystemIntegrityMonitor

**Coordination overhead — exists because of multi-agent complexity:**
- ContextAffinityService — solves a problem (domain familiarity decay) that doesn't exist for AI agents. There is no "familiarity decay." You either inject the context or you don't.
- ConflictDetectionService (41KB) — goal-to-goal and resource conflicts only arise with multiple concurrent work streams. Dependency cycle detection is the only piece needed regardless of architecture.
- FeedbackAggregationService — pattern detection across multiple workers. With better decomposition and verification, individual work item feedback is handled directly.

### 3.3 Key Structural Problems

1. **Characterization gate blocks all execution**: When any characterization is pending for a project, all execution work for that project is deferred (work_orchestrator.py). One slow characterization stalls everything.

2. **Skill matching is naive**: SkillSelectionService uses set intersection of capability strings with a "general" fallback. No semantic matching, no quality scoring.

3. **Context affinity is in-memory only**: Lost on serving restart. Solving a problem that shouldn't exist.

4. **First-available instance selection**: CoordinatingTeamService picks `instances[0]`. No capability weighting.

5. **Zero retries by default**: `max_retries: int = 0` in the orchestrator constructor.

6. **Feedback threshold too high**: `PATTERN_THRESHOLD = 3` signals required for pattern detection. With 2-3 workers, patterns never trigger.

7. **Work items can overlap in scope**: No deduplication mechanism. If decomposition produces overlapping work items, both execute fully — exactly the step repetition problem (MAST FM-1.3, 15.7% of all failures).

## 4. v2.0 Architecture: Three-Layer Intelligence Model

### 4.1 Design Philosophy

**Core principle**: ClaudeVN does not compete with Claude Code in the execution space. Users already have Claude Code. ClaudeVN adds value above and below execution:

- **Above**: Decomposing ambiguous goals into well-specified, independent work units (Layer 1)
- **Below**: Verifying that independently-produced outputs integrate correctly (Layer 3)
- **Around**: Preparing each execution instance for maximum efficiency (Layer 2, minimal)

**AI-native design principles:**

1. **Structured state over conversation**: Where possible, exchange typed data structures (diffs, ASTs, dependency graphs, formal specs) between layers rather than natural language summaries
2. **Single-pass execution over iterative exploration**: Front-load context so instances spend fewer turns exploring and more turns producing
3. **Computational verification over AI-as-reviewer**: Tests, static analysis, type checking, AST comparison — anything that can be computed should be computed, not delegated to another LLM to "judge"
4. **Independence by design**: Work units that truly share no state during execution. If they must share state, they aren't independent and should be a single work unit

### 4.2 Layer 1: Decomposition Intelligence

**Purpose**: Transform an ambiguous goal into formally specified, independent work units with verification criteria.

**This is the primary value driver.** The Agentless paper proved that the quality of problem specification directly determines execution success. ClaudeVN's Layer 1 is the human-AI collaboration interface for getting the specification right.

#### 4.2.1 Goal Analysis

Input: natural language goal from the user.

Process:
1. **Codebase analysis**: Programmatic analysis of the repository — file tree, dependency graph, module boundaries, interface definitions, test coverage. Not LLM exploration — static analysis tooling.
2. **Scope identification**: LLM-assisted identification of which parts of the codebase are affected, using the programmatic analysis as input.
3. **Independence boundary detection**: Identify natural seams where work can be split without shared state during execution. Seams are defined by: separate files/modules, separate test suites, no shared mutable state, well-defined interface contracts.

#### 4.2.2 Work Unit Specification

Each work unit produced by decomposition includes:

```yaml
work_unit:
  id: string
  goal_ref: string

  # What to do
  description: string                    # Natural language for human review
  formal_spec:
    target_files: [string]               # Exact files to modify
    interface_contracts:                  # What this unit must conform to
      - file: string
        type: "imports" | "exports" | "schema" | "api"
        definition: string               # The interface it must respect
    input_state: string                  # Git ref / branch this starts from
    expected_output:
      - type: "file_modified" | "file_created" | "file_deleted"
        path: string
        constraints: [string]            # e.g., "must export function X with signature Y"

  # How to verify
  verification_criteria:
    automated:
      - type: "test_pass" | "lint_clean" | "type_check" | "build_success"
        target: string
    integration:
      - type: "interface_compatible"
        with_unit: string                # Another work unit's ID
        contract: string

  # Context to inject
  context_package:
    files: [string]                      # Pre-identified files to include
    dependencies: [string]               # Output specs from upstream work units
    relevant_tests: [string]             # Existing tests that must continue passing

  # Independence assertion
  independence:
    shares_files_with: [string]          # Other units touching same files (should be empty)
    depends_on: [string]                 # Must complete before this starts
    depended_by: [string]               # Waiting on this to complete
```

#### 4.2.3 Interactive Refinement

The decomposition is presented to the user for review before execution begins. The UI supports:

- **Dependency graph visualization**: See the DAG of work units, identify bottlenecks
- **Independence audit**: Highlighted warnings where work units share files or have implicit coupling
- **Scope challenge**: "This unit touches 15 files — should it be split further?"
- **Verification review**: "Are these the right success criteria for this unit?"
- **Recomposition**: Merge units that are too granular, split units that are too broad

This is the primary human-AI collaboration interface. The user's judgment about decomposition quality is the highest-leverage input in the entire system.

#### 4.2.4 What to Retain from v1.0

- **GoalDecomposerService**: Core decomposition logic, enhanced to produce formal specs instead of English descriptions
- **DecompositionValidationService**: Cycle detection, dependency validation. Extend with independence verification.
- **WorkPlannerService**: Execution ordering from the dependency DAG. Simplify — bucket trees and planner profiles add complexity without clear evidence of value.

#### 4.2.5 What to Remove from v1.0

- **CharacterizationService** (as a separate compute dispatch): Fold into the decomposition phase. Characterization should happen during decomposition, not as a separate blocking gate.
- **PlannerProfileService**: Dynamic weight shifting based on aggregated worker feedback. This is coordination overhead from the multi-agent paradigm.
- **ConflictDetectionService** (goal-to-goal, resource conflicts): These conflict types arise from multi-stream coordination. Retain only dependency cycle detection.

### 4.3 Layer 2: Efficient Execution

**Purpose**: Make each Claude Code instance maximally effective through context preparation, then get out of the way.

**Design principle**: Layer 2 should be boring. If it needs intelligence, the decomposition in Layer 1 was insufficient.

#### 4.3.1 Context Assembly

Before dispatching work to a Claude Code instance, assemble a **context package**:

1. **Target files**: The actual file contents the instance will need to modify, identified during decomposition
2. **Interface definitions**: Types, function signatures, API schemas from adjacent modules
3. **Relevant tests**: Existing tests that must continue passing, plus generated verification tests
4. **Upstream outputs**: If this unit depends on a completed upstream unit, include the diff/output
5. **Formal specification**: The work unit spec from Layer 1

This is injected as a composed CLAUDE.md / task prompt. The instance receives **everything it needs in one shot** — no exploration phase required.

**Prompt caching note**: Within a Claude Code subscription session, the system prompt and CLAUDE.md are cached automatically. A well-constructed, stable context package means the instance's internal caching works efficiently across turns. The goal is to minimize turns, not cache hits — but caching makes even multi-turn sessions cheaper.

#### 4.3.2 Dispatch

Dramatically simplified from v1.0:

```
READY work units (dependencies satisfied)
    |
    v
Priority queue (from dependency DAG topological order)
    |
    v
Available Claude Code instance?
    |-- No: wait (simple queue, not market bidding)
    |-- Yes: inject context package, dispatch
    |
    v
Instance executes autonomously
    |
    v
Result (branch + PR) submitted to Layer 3
```

No affinity scoring. No skill matching beyond basic capability (does this instance have the right runtime?). No feedback aggregation. No conflict detection during execution. No multi-round orchestration.

The dispatch layer is a **priority queue with capability routing**. Not an orchestration engine.

#### 4.3.3 What to Retain from v1.0

- **WorkDispatcher**: Simplified to a priority queue
- **SSEConnectionManager**: Communication with compute instances
- **ClaudeCodeSpawner**: Instance lifecycle management (simplified)
- **Basic assignment tracking**: Know which instance is working on what, detect timeouts

#### 4.3.4 What to Remove from v1.0

- **WorkOrchestrator** (75KB): Replace with a simple dispatch loop (~5KB)
- **ContextAffinityService**: No longer needed — context is injected, not built through familiarity
- **FeedbackAggregationService**: Individual work item feedback goes directly to Layer 3 verification, not aggregated into planner profile adjustments
- **Coordinating team service**: First-available with capability check is sufficient
- **Most of AssignmentService** (37KB): Retain status tracking, remove the complex assignment scoring logic

### 4.4 Layer 3: Integration Verification

**Purpose**: Verify that independently-produced outputs integrate correctly and meet quality standards. This is the primary quality mechanism — the system catches problems through verification, not through coordination.

**Design principle**: Prefer computation over judgment. Every check that can be automated should be automated. LLM-based review is a fallback for what computation can't catch.

#### 4.4.1 Per-Unit Verification (Automated)

When a work unit completes (PR submitted), run the verification criteria from its spec:

1. **Build success**: Does it compile/build?
2. **Test pass**: Do all specified tests pass (existing + generated)?
3. **Lint/type check**: Static analysis clean?
4. **Spec compliance**: Do the changes touch only the files specified? Do they export the interfaces specified?
5. **Scope containment**: Did the instance modify files outside its work unit's scope? (Flag for human review if so — may indicate decomposition was wrong)

These are **computational checks**, not LLM judgments. They run as CI-style pipelines on the submitted branch.

#### 4.4.2 Cross-Unit Integration Verification

This is ClaudeVN's **unique value** — the thing no individual Claude Code instance can do.

When multiple work units complete:

1. **Interface compatibility**: Do the outputs of Unit A conform to the interface contracts expected by Unit B? (Type checking, schema validation, import/export analysis)
2. **Merge safety**: Do the branches merge cleanly? If not, what's the conflict scope?
3. **Combined test suite**: Does the merged result pass the full test suite?
4. **Cumulative static analysis**: What's the change in warnings/complexity across the combined diff? (Directly addressing the MSR 2026 finding about AI tools increasing complexity by 41%)
5. **Gap detection**: Are there parts of the original goal not covered by any work unit? (Decomposition quality feedback)

#### 4.4.3 Human Review Interface

Layer 3's UI presents:

- **Per-unit verification results**: Pass/fail per criterion, with details on failures
- **Integration status**: Which units integrate cleanly, which have conflicts
- **Combined diff view**: The total change to the codebase, annotated with which work unit produced each change
- **Quality metrics**: Complexity change, test coverage change, static analysis delta
- **Gap analysis**: What the goal asked for vs. what was delivered
- **Decision points**: Where human judgment is needed (scope violations, integration conflicts, ambiguous verification results)

#### 4.4.4 Verification-Driven Iteration

When verification fails:

1. **Automated fix attempt**: For well-defined failures (test failure with clear error, lint violation, type error), resubmit to the same Claude Code instance with the failure information and the formal spec. Single retry — not an infinite loop.
2. **Decomposition feedback**: If the failure suggests the decomposition was wrong (scope violation, interface mismatch), surface this to the user in the Layer 1 UI for re-decomposition.
3. **Human escalation**: For ambiguous failures or repeated failures, present to the user with full context.

#### 4.4.5 What to Retain from v1.0

- **QualityGateService**: Core verification logic. Extend with formal spec compliance checking and cross-unit integration analysis.
- **SystemIntegrityMonitor**: Pipeline health monitoring. Simplify — fewer state machines means fewer anomalies to detect.

#### 4.4.6 What to Remove from v1.0

- **LeadComputeService**: AI-reviewing-AI via a separate Claude Code instance. Replace with computational verification. The subscription cost of running a review instance is better spent on an execution instance.

## 6. AI-Native Design Considerations

### 6.1 Why Current Agent Architectures Fight the Medium

Current ClaudeVN (and most agent frameworks) treat LLMs as simulated human workers:

| Human Pattern | AI-Native Alternative | v2.0 Approach |
|---|---|---|
| Turn-based conversation between agents | Structured data exchange (diffs, ASTs, specs) | Work units exchange typed specs, not English summaries |
| Iterative codebase exploration ("let me poke around") | Programmatic context assembly + single-pass injection | Context package assembled before dispatch |
| Role-playing personas ("you are a senior reviewer") | Formal verification specifications | Verification criteria are computable checks, not review instructions |
| Planning as sequential text generation | Dependency DAGs with formal pre/postconditions | Work unit specs include input_state, expected_output, verification_criteria |
| Familiarity-based assignment (context affinity) | Context injection (no familiarity needed) | Any instance can do any work with proper context |
| Multi-round self-correction loops | Single-pass generation + external verification + targeted retry | Execute once, verify computationally, retry with specific failure info if needed |

### 6.2 Where Human Judgment Remains Essential

The research is clear that AI agents struggle with:

1. **Problem understanding**: Interpreting ambiguous goals, identifying unstated requirements, understanding business context. This is Layer 1's interactive decomposition.
2. **Integration judgment**: Deciding whether technically correct output actually meets the intent. Whether a combined diff "feels right" for the project's direction. This is Layer 3's human review interface.
3. **Decomposition validation**: Is this the right way to split the work? Are the independence boundaries real? This requires system-level architectural understanding.

v2.0 keeps humans in the loop at these points and removes them from the points where human involvement adds no value (execution monitoring, inter-agent coordination, style-based code review).

### 6.3 Design-Time vs. Execution-Time

A key insight from our analysis: the distinction between **design-time** (where exploration, competition, and human judgment add value) and **execution-time** (where determinism, speed, and verification matter) is fundamental.

| Aspect | Design-Time | Execution-Time |
|---|---|---|
| Goal | Understand the problem, specify the work | Produce the output |
| Mode | Exploratory, iterative, conversational | Deterministic, single-pass, pipeline |
| Human role | Active collaborator | Observer (via UI) |
| AI role | Assistant to human reasoning | Autonomous executor against spec |
| Quality mechanism | Human judgment + challenge | Computational verification |
| Value of coordination | High (multiple perspectives help) | Low to negative (overhead exceeds gains) |

v2.0 explicitly separates these modes and optimizes each independently.

## 7. Subscription Model Optimization

### 7.1 Constraint

ClaudeVN targets users with Claude Code subscriptions (Max plan or similar). The optimization target is **maximum value per subscription cycle**, not minimum cost per API token. This means:

- Every Claude Code instance turn spent on coordination, exploration, or redundant work is a turn not spent on productive output
- Running a separate "reviewer" instance costs the same as running a "worker" instance — use instances for production, not review
- Hitting rate limits faster means less work done per cycle — efficiency directly translates to throughput

### 7.2 Efficiency Gains

| v1.0 Pattern | Subscription Cost | v2.0 Pattern | Expected Improvement |
|---|---|---|---|
| Instance explores codebase (~15-20 turns) | High turn burn | Context pre-injected, instance starts producing immediately | 2-3x fewer turns per work unit |
| Separate LeadCompute instance reviews PRs | Full instance cost for review | Computational verification (no instance needed) | 1 instance freed per review cycle |
| Agents stuck in clarification loops | Wasted turns | Formal specs reduce ambiguity | Fewer wasted turns |
| Overlapping work units execute redundantly | Double instance cost | Independence assertion prevents overlap | No redundant execution |
| Coordination overhead (MCP calls, progress reports, context requests) | Turn overhead per instance | Minimal coordination — execute and report completion | Fewer turns on coordination |

### 7.3 Prompt Caching Within Sessions

Claude Code automatically caches system prompts, CLAUDE.md content, and tool definitions within a session. v2.0 optimizes for this:

- **Stable context packages**: The composed CLAUDE.md (skill instructions + context package) should be stable across turns within a session, maximizing cache hits at 10% of base input cost
- **Lean, task-specific composition**: Only include what the instance needs — bloated CLAUDE.md wastes context window on every turn
- **Front-loaded context**: Put the heaviest context (file contents, interface definitions) in the system prompt where it's cached, not in per-turn messages

## 8. Product Positioning

### 8.1 What ClaudeVN Is

**ClaudeVN is the intelligence layer that makes Claude Code work at project scale.**

For individual tasks, Claude Code is already excellent. For projects — multi-file changes, multi-step goals, work that spans modules and requires integration — a single Claude Code instance lacks the global view to decompose effectively, the context to specify precisely, and the scope to verify integration.

ClaudeVN provides:

1. **Decomposition engine**: Goal → formally specified, independent work units with verification criteria. Interactive refinement with the developer.
2. **Context assembler**: Per-work-unit context packages that make Claude Code sessions 2-3x more efficient by eliminating the exploration phase.
3. **Integration verifier**: Cross-session analysis that catches composition failures no single instance can see.

### 8.2 What ClaudeVN Is Not

- **Not an orchestration platform**: We don't manage agents. We prepare work and verify results.
- **Not a Claude Code replacement**: We don't compete in execution. We make execution more effective.
- **Not a dashboard**: Observability is a feature of each layer, not the product itself.
- **Not a marketplace**: Skill matching and market bidding add coordination overhead without evidence of value.

### 8.3 Competitive Moat

- **Layer 1 (Decomposition)** is the hardest to replicate because it requires deep codebase analysis + LLM reasoning + human interaction design. Anthropic is unlikely to build this into Claude Code because it's a product experience, not a model capability.
- **Layer 3 (Integration Verification)** requires the global view that individual sessions don't have. This is structural — no single-instance improvement can provide cross-session integration analysis.
- **Layer 2 (Context Preparation)** is the thinnest moat but still valuable — programmatic context assembly optimized for Claude Code's caching behavior is specialized knowledge.

## 10. Compute Provisioning Model

### 10.1 Compute Environments Are Derived from Planning

v1.0 assumed pre-configured compute types (generic Claude Code instances with optional runtime tools). v2.0 inverts this: **the compute environment is a product of Layer 1 planning**, not a pre-existing assumption.

When Layer 1 decomposes a goal into work units, it also analyzes what runtime capabilities those work units require — SDKs, build tools, test frameworks, linters, package managers. This analysis produces a **compute environment specification** (a Dockerfile or similar artifact) alongside the work unit specs.

### 10.2 Human-Gated Provisioning

Compute specs follow the same approval pattern as decompositions:

```
Layer 1 Planning
  ├── Work units        → human reviews → approves → enters dispatch queue
  └── Compute env spec  → human reviews → approves → image built / available
```

The system prepares but does not auto-provision. No Docker builds happen without explicit human approval. This prevents:
- Unexpected resource consumption
- Security risks from auto-generated Dockerfiles
- Environments that don't match the developer's expectations

### 10.3 Builder and Verifier Share the Same Environment

A single compute environment handles the full lifecycle for its work units: code implementation, test creation, and verification (lint, type check, build, test execution). Splitting builder and verifier into separate environments breaks the shared-toolchain requirement — the verifier needs the same runtime, same packages, same versions as the builder.

### 10.4 Parallelism Across Environments

Truly independent work units that target different environments can execute in parallel on separate compute instances. For example, a Python backend work unit and a Node frontend work unit with no shared files or dependencies can run concurrently.

Independence assertions from Layer 1 determine what can parallelize. The dispatch layer matches work unit requirements to approved compute environments.

### 10.5 Environment Evolution

If planning detects a new dependency mid-project (e.g., a Go microservice is added to what was a Python + Node project), it proposes an updated or additional compute spec for approval. The compute environment evolves with the project rather than constraining it.

### 10.6 Why Docker

Docker provides:
- **Reproducibility**: The Dockerfile is a versionable artifact of planning
- **Isolation**: Each compute runs in its own container with only what it needs
- **Flexibility**: Any combination of runtimes, SDKs, and tools — not limited to pre-baked types
- **Portability**: Same compute spec works locally, in CI, or on remote infrastructure

## 11. Open Questions

1. **Decomposition quality risk**: Bad decomposition is worse than no decomposition. How do we measure decomposition quality and build confidence before execution? The interactive refinement UI helps, but developers may rubber-stamp decompositions.

2. **True independence is hard to achieve in practice**: Many software changes have implicit coupling (shared configuration, transitive dependencies, runtime behavior that depends on multiple modules). How do we detect implicit coupling that isn't visible in static analysis?

3. **Granularity threshold**: At what point is a work unit too small (overhead exceeds value) or too large (loses the benefits of decomposition)? This likely varies by project and goal.

4. **Context package size vs. context window limits**: If a work unit needs 30 files of context, does it fit in the Claude Code context window? What's the compression strategy?

5. **Verification completeness**: Computational verification catches structural problems but may miss semantic issues (code that compiles and passes tests but doesn't actually do what was intended). Where is the line between what computation can verify and what needs human judgment?

6. **Multi-project / monorepo support**: The architecture assumes one project/repo per goal. How does this extend to monorepo or multi-service architectures?
