# ClaudeVN v1.0 Architecture

**Version**: 1.0.0
**Last Updated**: January 2026
**Status**: Design Document

---

## Overview

ClaudeVN v1.0 represents a fundamental architectural shift from custom Python microservices to **Claude Code-powered compute instances** with **Git-based state management**. This enables emergent, conversation-driven AI agent coordination where Claude Code serves as the execution engine.

### Key Paradigm Shifts

| Aspect | v0.x (Previous) | v1.0 (New) |
|--------|-----------------|------------|
| **Compute Engine** | Custom Python runtime with LLM providers | Claude Code instances |
| **Agent Definition** | JSON specs with prompts, capabilities | Skill CLAUDE.md fragments composed into agents |
| **Communication** | REST APIs, WebSocket, Event Bus | MCP tools + Git synchronization |
| **State Management** | Session contexts, DB storage | Git branches (1 branch = 1 work unit) |
| **Workflow** | Coordinating agents orchestrate | Dynamic, resource-driven mapping |
| **Marketplace** | Persona definitions embedded | Separate Skill Marketplace service (port 8003) |

## Components

### 1. Serving (Central Hub)

The Serving component is the **exclusive coordination server** that manages all work distribution, state, and communication.

#### Responsibilities

| Function | Description |
|----------|-------------|
| **Skill Marketplace** | Registry of atomic skills composed into agents for Claude Code instances |
| **MCP Server** | Exposes tools for Claude Code instances to call |
| **Slim Claude Code** | Intent-based orchestration - Goal Decomposer + Work Planner (see [spec](../specifications/slim-claude-code.md)) |
| **Work Map** | Dynamic task allocation and dependency tracking |
| **Compute Registry** | Tracks active Claude Code instances and their status |
| **Git Server** | Hosts the "true copy" repository (source of truth) |
| **PR Management** | Redis-backed queue for branch status and merge coordination |
| **Monitoring UI** | Real-time WebSocket dashboard for work visibility |

#### Key Principles

1. **Single Source of Truth**: Serving owns the canonical Git repository
2. **Work Distribution**: Serving assigns tasks and composed agents (from skills) to compute instances
3. **Merge Authority**: Only Serving can merge branches to main
4. **State Coordination**: All state flows through Serving

### 2. Compute Instances (Claude Code Workers)

Compute instances are **Claude Code processes** that execute work autonomously.

#### Characteristics

| Aspect | Description |
|--------|-------------|
| **Runtime** | Claude Code CLI with full tool access |
| **Identity** | Agent composed from skills (merged CLAUDE.md) |
| **State** | Git clone with feature branch |
| **Communication** | MCP tools to Serving, Git push/pull |
| **Lifecycle** | Spawned by Serving with context, runs until task complete |

#### Workspace Structure

```
/workspace/                      # Compute's workspace root (Git clone)
├── .git/                        # Git directory
└── ...                          # Working directory on feature branch
                                 # e.g., f/task-123/compute-001
```

**Note:** Each Compute handles one task at a time. Simple branch workflow - no worktrees needed.

#### Rules

1. **Never push to main**: Work on feature branches only
2. **All work on branches**: Create branch from main, work, push
3. **One primary task**: Each compute focuses on one task at a time
4. **Report progress**: Use MCP tools to update Serving on status

### 3. Skill Marketplace (Separate Service)

The Marketplace is a **separate service** (port 8003) that manages skills and agent composition. Serving's UI displays skill data sourced from Marketplace via HTTP.

Skills are **atomic capability units** that get composed into agents for Claude Code instances.

#### Skill Definition (CLAUDE.md Fragment)

```markdown
# {Skill Name}

## Instructions
{What this skill enables the agent to do}

## Capabilities
- {Capability 1}
- {Capability 2}

## Constraints
- {Constraint 1}
- {Constraint 2}
```

Skills are composed by Serving's Claude Code instance into complete Agent bundles with merged instructions.

#### Example Skills

| Skill | Capabilities | Description |
|-------|--------------|-------------|
| **code-implementation** | Write/modify code | Implements features following project conventions |
| **code-analysis** | Review code quality | Reviews changes for issues and best practices |
| **test-creation** | Write tests | Creates unit/integration tests |
| **bug-investigation** | Debug issues | Investigates bugs, traces root causes |
| **documentation** | Write docs | Creates READMEs, API docs, guides |

See [Skill Marketplace Specification](../specifications/skill-marketplace.md) for full details.

## Communication Patterns

### 1. MCP Tools (Compute → Serving)

Claude Code instances use MCP tools to communicate with Serving:

```
┌────────────────────┐     MCP Call      ┌────────────────────┐
│  Claude Code       │ ────────────────> │  Serving           │
│  (Compute)         │                   │  (MCP Server)      │
│                    │ <──────────────── │                    │
│                    │     Response      │                    │
└────────────────────┘                   └────────────────────┘
```

#### Available MCP Tools

**Compute Infra Layer:**

| Tool | Purpose |
|------|---------|
| `claudevn_get_assignment` | Fetch full assignment after SSE notification |

**Claude Code (Worker) Tools:**

| Tool | Purpose |
|------|---------|
| `claudevn_report_progress` | Update task status (started, blocked, progress %) |
| `claudevn_request_review` | Signal branch ready for review |
| `claudevn_get_context` | Fetch relevant project context |
| `claudevn_signal_blocker` | Report blockers/dependencies |
| `claudevn_complete_task` | Mark task complete, request merge |
| `claudevn_add_requirement` | Add discovered work items to backlog |

**Note:** `claudevn_get_skill` was removed - skills are composed by Serving and included in the assignment response.

### 2. Git Communication (Compute ↔ Serving)

All file-based state flows through Git:

```
┌────────────────────┐                   ┌────────────────────┐
│  Compute           │                   │  Serving           │
│  (Local Repo)      │                   │  (Bare Repo)       │
│                    │                   │                    │
│  git pull ─────────────────────────────> (fetch main)      │
│                    │                   │                    │
│  git push ─────────────────────────────> (push branch)     │
│                    │   SSH             │                    │
└────────────────────┘                   └────────────────────┘
```

### 3. Event Flow (Notification + Fetch Pattern)

Serving notifies Compute Infra of available work; Compute fetches full details:

```
1. Serving receives task/goal
2. Serving pushes lightweight SSE event: work_assigned { task_id }
3. Compute Infra calls claudevn_get_assignment(task_id) via MCP
4. Serving selects skills, composes agent, returns full assignment
5. Compute Infra spawns Claude Code with assignment
6. Claude Code begins work
7. Progress reported via MCP tools
8. Work pushed via Git
9. Serving merges when approved
```

**Why Notification + Fetch?** Serving cannot directly call Compute APIs (NAT, firewalls). SSE pushes notifications; Compute pulls details when ready.

## Git Infrastructure

### Components

| Component | Purpose |
|-----------|---------|
| **Bare Repos** | Source of truth storage (`/repos/{project}.git`) |
| **SSH Daemon** | Git transport with key-based auth |
| **Git Hooks** | Trigger events on push (post-receive) |
| **Redis** | PR queue, branch status, merge coordination |
| **PR Manager API** | Create, approve, merge, list PRs |

### Branch Naming Convention

```
{type}/{task-slug}/{compute-id}

Types:
  f/   - feature
  x/   - fix
  r/   - refactor
  t/   - test
  d/   - docs

Examples:
  f/implement-user-auth/compute-001
  x/fix-login-bug/compute-023
  r/cleanup-api-routes/compute-007
```

### Branch Lifecycle

```
1. CREATE    git checkout -b f/task/compute-id   (from main)
2. WORK      <Claude Code works, commits>
3. PUSH      git push origin f/task/compute-id
4. PR        claudevn_request_review()            (MCP call)
5. REVIEW    <Reviewer examines, approves/rejects>
6. MERGE     Serving merges to main              (or reject → resolve)
7. CLEANUP   Branch retained for history
```

### Conflict Resolution

When a branch conflicts with main:

```
1. Serving attempts merge
2. Conflict detected
3. Serving rejects PR with reason
4. Original compute notified (status=conflict)
5. Compute rebases branch onto latest main
6. Compute pushes updated branch
7. Re-review triggered
```

### Redis Schema

```
# Branch metadata
branch:{project}:{branch_name} = {
  status: pending | in_review | approved | rejected | merged | conflict,
  compute_id: compute-001,
  task_id: task-123,
  created_at: ISO timestamp,
  last_commit: SHA
}

# PR queue (branches ready for review)
pr_queue:{project} = sorted set { branch_name: timestamp }

# Merge queue (approved, waiting to merge)
merge_queue:{project} = list [branch1, branch2, ...]

# Compute active branches
compute:{compute_id}:branches = set {branch1, branch2}
```

## Work Distribution

### No Fixed Workflow

ClaudeVN v1.0 operates with **dynamic, resource-driven task allocation**:

1. **Goal arrives** at Serving
2. **Slim Claude Code** analyzes goal, breaks into tasks
3. **Work Map** updated with tasks and dependencies
4. **Available compute** checked for capacity
5. **Skills selected** and composed into agent based on task requirements
6. **Task assigned** to compute instance with composed agent
7. **Progress monitored** via MCP reports
8. **Results synthesized** when tasks complete

### Task Assignment Algorithm

```python
def assign_task(task):
    # 1. Check dependencies
    if task.blocked_by:
        return None  # Wait for blockers to resolve

    # 2. Select skills and compose agent
    skills = select_skills(task.required_capabilities)
    agent = compose_agent(skills, task)

    # 3. Find available compute
    compute = find_available_compute()

    # 4. Spawn/assign
    if compute.idle:
        send_context_and_start(compute, task, agent)
    else:
        spawn_new_compute(task, agent)

    return assignment
```

## Deployment Model

### Per-Project Isolation

- **One Serving instance per project**
- **One bare repo per project**
- **Multiple compute instances per project**
- **Projects run side-by-side independently**

### Scaling

| Component | Scaling Model |
|-----------|---------------|
| **Serving** | Vertical (single instance per project) |
| **Compute** | Horizontal (spawn more Claude Code instances) |
| **Git** | Vertical (single repo per project) |
| **Redis** | Horizontal (cluster for large deployments) |

## Security Model

### Authentication

| Connection | Method |
|------------|--------|
| **Compute → Serving (MCP)** | API key per compute instance |
| **Compute → Git (SSH)** | SSH key per compute instance |
| **User → Serving (UI)** | Session-based auth |

### Authorization

| Action | Who Can Perform |
|--------|-----------------|
| **Create task** | Serving (slim Claude Code) |
| **Assign work** | Serving |
| **Push branches** | Compute instances (not main) |
| **Merge to main** | Serving only |
| **View status** | Authenticated users |

## Migration from v0.x

### Components Removed

| v0.x Component | Reason |
|----------------|--------|
| **Marketplace service** | Replaced by Skill Marketplace in Serving |
| **Compute runtime** | Replaced by Claude Code |
| **LLM providers** | Claude Code has built-in LLM |
| **Tool executor** | Claude Code has native tool execution |
| **A2A protocol** | Replaced by MCP + Git |

### Components Transformed

| v0.x → v1.0 | Changes |
|-------------|---------|
| **Serving** | Adds Git server, MCP server, skill marketplace |
| **Process Maps** | Becomes Work Map (Git branch-based) |
| **Sessions** | Becomes project work context |
| **Observability** | Git activity + MCP status reports |

### Data Migration

1. **Agent definitions** → Skills (CLAUDE.md fragments) composed into agents
2. **Session state** → Git branches + Work Map
3. **Event history** → Git commit history + Redis logs
